2 · The mailbox trick — no lookup table

The test knows…

plan it just created → planId: abc123
event it waits for → plan-status-canceled

The event carries…

payment_plan_id: abc123
event: plan-status-canceled
↘   both independently compute   ↙
e2e-await-abc123-plan-status-canceled

The test names a child workflow with that string and waits on it. The bridge formats the same string from the event's own fields and signals it. They never talk to each other — the naming convention IS the routing table. Zero state in the bridge.

4 · One subscription per worker — why

✗ Shared subscription

a subscription is a queue — each message goes to ONE consumer
topic

events split randomly → A steals B's event → B's test hangs

✓ Per-instance subscription

each subscription gets a FULL copy of every message
topic
dev A 😀
dev B 😀
everyone sees everything — e2e-bridge-{user}-{rand}, 24h self-destruct

Staging volume ≈ 2 events/min, so duplicating the stream to every dev is free.

5 · Why nothing collides (shared topic, by design)

Subscription layerevery bridge gets its own full copy — nothing to fight over receiving
Routing layerbridge signals its own local Temporal only. Your event on my laptop → WorkflowNotFound → silently dropped. Not-found is the normal case.
Identity layerplan IDs are globally unique per run + event type is in the mailbox name → even two waits in the same test get distinct mailboxes

There is no shared mutable thing anywhere in the path — so there's nothing to collide on.

⚠️ One gap to know: a subscription only receives events published after it exists. Worker down when the event fires → event missed → manual rescue signal (one CLI line, in the README). The future central deployment uses a stable, permanent subscription — events queue while the consumer restarts, gap closed.
